### Почему старые 1,8–2,6 tok/s и новые 15 tok/s различаются

Старый отчёт `frame-l3-20261003` сохранил итоговые 1,8–2,6 tok/s и пометил Tiel как 26 слотов, но не сохранил точную команду, контекст, число/режим имитаторов и сырые пары. Текущий CPU-only C на Tiel использовал 16 слотов, контекст 186540, `-t6`, `--poll` по умолчанию 50, шесть LCG-процессов без больших обращений к памяти; он дал 15,13 tok/s.

Чтобы проверить, не был ли старый результат артефактом, повторён один C-проход с теми же Tiel/16 slots/186540 tokens/`-t6`/poll50/temperature0/seed1, но с шестью непрерывными `memmove`-процессами, каждый копировал 16 МиБ. Получено 1,95 и 1,75 tok/s (медиана 1,85), что воспроизводит прежний диапазон. Значит, сильнее всего скорость уронила нагрузка на пропускную способность RAM, а не само значение `--poll`; изменение 26→16 слотов не объясняет падение до ~2 tok/s. Полностью доказать идентичность исторического сценария нельзя: его сырые параметры утеряны.

Этот memory-copy прогон остановлен по неизменному single-hiccup порогу: проба зафиксировала 53,35 мс. До остановки p99 кадров был около 12,9 мс, jank 0,22–0,29%, свободная VRAM не опускалась ниже 286 МиБ, температуры — GPU 58°C / CPU Tctl 49,4°C. Третью выборку не запускали.

CPUQuota 500% / 5 мс ранее вызвал одиночный кадровый пик 78,42 мс; эту настройку не повторяли. Рабочий профиль не меняли.

## L2: падение backend и сохранение сессии

| Сценарий | Tiel | Occamy |
|---|---|---|
| SIGKILL до первого байта | После исправления gateway перезапустил сервер и повторил запрос; `cache_n=186540`, `prompt_n=35` | То же: `cache_n=186540`, `prompt_n=35` |
| SIGKILL после SSE-байта | `HTTP 200`, в поток добавлен `SHURA_RESPONSE_INTERRUPTED`, `[DONE]` отсутствует, replay=0 | То же; первый SSE-пакет был получен до SIGKILL, replay=0 |
| Crash report | SIGKILL, журнал сервиса и очищенные argv; файлы меньше 64 КиБ | То же |

Первый no-byte прогон вернул 503: socket закрывался раньше, чем `Popen.poll()` видел завершение процесса. Второй дефект обнаружен при retry: после restore сервер сообщал `n_prompt_tokens=0`, и gateway отбрасывал сохранённый disk A2 как пустую сессию. Исправлено: gateway коротко ждёт подтверждения выхода child и сохраняет право восстановить уже имеющийся проверенный disk A2 при нулевом числе новых prompt-токенов. Добавлены unit-тесты на задержанный код выхода, живой backend и сохранение disk A2; L2 повторно прошёл на обеих моделях.

После первого SSE-байта повтор не выполняется. Ранее проверенный OpenCode 1.18.32 завершает такую попытку ошибкой потока и кодом завершения 1; основной запрос не запускается второй раз. Это намеренно требует ручного продолжения неполного ответа.

## L3: ShuraCode и давление VRAM

Для каждой модели запущена изолированная реальная ShuraCode CLI-сессия в `/dev/shm`, с отдельными `HOME`/XDG, `stdin=DEVNULL`, собственным рабочим каталогом и выключенными MCP/плагинами. По три последовательных шага, все команды завершились с кодом 0, тесты временного проекта прошли. Контроллер был включён, но профиль удерживался на безопасном минимуме 16 слотов: изменений gear и пауз перезапуска не было.

Предварительный ShuraCode запуск без явного `--title` получил `SHURA_CHECKPOINT_NOT_READY` до ответа backend. Точный счётчик одновременных запросов в тот момент не записался; итоговый изолированный прогон запускал с явным заголовком, после чего три шага прошли. В stdout также попал текст движка `MAXIMUM STEPS REACHED` при выставленном тестовом лимите build-agent в 5 шагов; CLI вернул 0, а последующие `--continue` шаги и тесты проекта прошли.

Рамп +100/+200/+280 МиБ не запускался. Предварительная проверка учитывала измеренный CUDA context helper (~182 МиБ) и дополнительный запас до жёстких 150 МиБ. Для Tiel при первом шаге свободно было414 МиБ: +100 вместе с контекстом дало бы прогноз94 МиБ. Для Occamy перед +100 было470 МиБ: прогноз150 МиБ, ниже принятого preflight-запаса180. Для +200 и +280 прогноз был ещё ниже. Эти шаги безопасно отклонены до выделения; реальное поведение gear под нагрузкой поэтому не доказано.

Отдельная первая попытка Tiel действительно выделила +100 без учёта контекста helper и остановилась при146 МиБ. Снимок в этот момент: llama-server 10346 МиБ, helper282 МиБ, Brave199 МиБ, KWin129 МиБ, plasmashell149 МиБ, plasma-keyboard62 МиБ, System Settings163 МиБ, Telegram27 МиБ, прочие перечислены в сыром временном логе. Сумма видимых desktop-процессов была около775 МиБ; скачок desktop до1,7 ГиБ в этих снимках не воспроизвёлся. Исторические Tiel 20-slot остановки 132/116 МиБ не содержали списка процессов, поэтому их причину задним числом установить нельзя.

Был также load-PSI стоп Occamy: `memory full avg10=10,49%`, MemAvailable5,88 ГиБ, zram 8388604 КиБ из 8388604 КиБ (100%), RSS top-10 записан во временной телеметрии; лидировали llama-server11,7 ГиБ, ChatGPT637 МиБ, ShuraCode556 МиБ, VS Code465 МиБ и Brave-процессы. Дискового swap не было; `/proc/swaps` показывал только `/dev/zram0`. После паузы запуск продолжен, hard-порог не менялся.
