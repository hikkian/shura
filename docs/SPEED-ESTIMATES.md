# Прогноз скорости на Vulkan: калибровка по открытым данным

Задача PUB5. Расчёт: `reports/pub5/calibrate_vulkan.py`, строки с источниками: `reports/pub5/vulkan_rows.csv`,
коэффициенты: `catalog/speed-calibration-vulkan.json`. Код установщика (`installer/universal/planner.py`) этой задачей не
менялся: его правит задача PUB3.

## Метод

Генерация токенов ограничена пропускной способностью памяти. Для каждого замера:

    эффективность = tok/s декода (llama-bench tg128) × байты, читаемые за токен / пиковая пропускная способность

- Плотная модель: байты за токен ≈ размер файла. Опора: `llama-2-7b.Q4_0.gguf`, 3.83 ГБ (размер Q4_0-файла той же
  архитектуры по странице с файлом на Hugging Face; сам файл `llama-2-7b.Q4_0` не открывал).
- MoE `Qwen3-30B-A3B` Q4_K_M: байты за токен ≈ 2.0 ГБ (3.3 млрд активных параметров × около 4.9 бит). Размер файла
  (около 18.6 ГБ) взят из памяти, по страницам не проверен.
- Пиковая пропускная способность: спецификации производителей. Значение RX 7800 XT (624 ГБ/с: шина 256 бит, 19.5 Гбит/с)
  сверено через поиск; остальные взяты по спецификациям и не сверялись.

Это разброс около ±13 % у одной и той же карты между сборками.

## MoE, Vulkan, Qwen3-30B-A3B Q4_K_M

Источник: пост на форуме Radxa, [forum.radxa.com/t/llama-cpp-benchmarks/27813/17](https://forum.radxa.com/t/llama-cpp-benchmarks/27813/17).
RX 7900 XTX (RADV NAVI31), сборка c55d53ace, `ngl 99`, 4 варианта с разными `taskset`.

| прогон | tok/s декода | эффективность (при 960 ГБ/с, 2.0 ГБ/токен) |
|---|---|---|
| без закрепления ядер | 57.64 | 0.12 |
| `taskset`, `-t 8` | 61.92 | 0.13 |
| `taskset`, `-t 1` | 62.28 | 0.13 |

Оговорка, по которой эта строка не годится для точной подгонки: тот же пост даёт этой же карте 99.8 tok/s (fa 0) на
плотной Llama 2 7B Q4_0, а в таблице #10879 она даёт 182.6. Разница вдвое говорит о другой сборке или настройке. Поэтому
эффективность MoE на Vulkan — одна точка от одного источника. Она согласуется с обсуждением
[#17751](https://github.com/ggml-org/llama.cpp/issues/17751): там для MoE на Vulkan в первую очередь тормозит
`mul_mat_ids`, а не память. Другой MoE-замер на Vulkan (Renoir APU, Qwen3-30B-A3B-Thinking, 20.9 tok/s) не берём:
пропускная способность памяти этой системы в посте не указана.

## Сравнение с текущими коэффициентами установщика

Текущий коэффициент для GPU в `planner.py` — `efficiency.gpu = 0.5` (для MoE на GPU — `efficiency.hybrid = 0.30`).
Прогноз по формуле `скорость = эффективность × пропускная способность / байты` против измеренного:

| карта, модель | измерено, tok/s | прогноз с 0.5 | ошибка | прогноз с 0.67 (плотные) / 0.12 (MoE) | ошибка |
|---|---|---|---|---|---|
| RX 7800 XT, Llama 2 7B Q4_0, без FA | 118.3 | 81.5 | −31 % | 109.1 | −8 % |
| RX 7900 XTX, Qwen3-30B-A3B Q4_K_M | 62.3 (макс.) | 240 | +285 % | 57.6 | −8 % |

Вывод: для плотных моделей на Vulkan текущий коэффициент занижает скорость примерно на четверть. Для MoE на Vulkan он
завышает скорость в несколько раз. Это важно: по этой ошибке установщик на AMD с Vulkan может обещать скорость, которой
не будет.

## Применено в установщике (PUB5b)

Коэффициенты внесены в `installer/universal/planner.py` (`DEFAULTS`: `vulkan_efficiency`, `vulkan_label`). Тест
`tests/test_speed_calibration.py` проверяет, что числа совпадают с `catalog/speed-calibration-vulkan.json`.

| параметр | было | стало | основание |
|---|---|---|---|
| эффективность плотных моделей, Vulkan (все GPU, кроме Intel) | 0.5 (общая для GPU) | **0.67** | нижний квартиль RDNA3+NVIDIA, 20 строк; осторожно, как и весь планировщик |
| эффективность плотных моделей, Intel Arc, Vulkan | 0.5 | **0.43** | медиана четырёх строк Arc (0.32–0.59); без этого Arc переоценивается примерно на 55 % |
| эффективность MoE, Vulkan | 0.30 (hybrid) / 0.5 (gpu) | **0.12** | одна карта, один источник; до второго замера ставим нижнюю границу |
| подпись плотных, Vulkan | нет | **«оценка, ±20 %»** | 18 из 20 строк RDNA3/NVIDIA (90 %) лежат в ±20 % от медианы 0.72 |
| подпись MoE и Intel, Vulkan | нет | **«оценка, ±50 %, мало данных»** | одна карта (MoE) и четыре строки (Intel) |
| HIP, CUDA, Metal | без изменений | без изменений | путь HIP (наш форк) и CUDA откалиброваны отдельно (`hipfork_time_penalty`, `fork`) |

Подпись выводится в строке «Expected» карточки установщика, рядом с прогнозом. Для путей, которые не откалиброваны этими
числами (форк CUDA, TurboQuant+, Metal, частичное размещение плотной модели), подписи нет, как и раньше.

Подпись для калибровки на машине пользователя («измерено, ±N %») установщик выводит после реального замера; этот документ
касается только предварительного прогноза.

Выбор, который сделан без задания: Intel Arc получил отдельный коэффициент (0.43) и подпись ±50 %. Пункт карточки говорил
про «бэкенд и тип модели», а Intel в данных заметно ниже остальных; без отдельного коэффициента прогноз для Arc был бы
завышен примерно на 55 %.

Подпись для калибровки на машине пользователя («измерено, ±N %») установщик выводит после реального замера; этот документ
касается только предварительного прогноза.

## Наша машина (опора, не часть подгонки)

RX 7800 XT, HIP (наш форк), MoE в гибридной раскладке, из [REPORT-LAYOUT1c](../reports/REPORT-LAYOUT1c.md) (ветка другой

## Что НЕ проверено

- Открытые таблицы сняты через пересказ страниц (WebFetch), построчно по исходным страницам не сверялись. Значения tg128
  внутри таблиц совпадают с пересказом, но ошибка переписывания возможна.
- Пиковая пропускная способность всех карт, кроме RX 7800 XT, — по спецификациям из памяти, без поиска.
- Размер Qwen3-30B-A3B Q4_K_M (18.6 ГБ) и активные байты MoE — оценки.
- Нет ни одного Vulkan-замера MoE на RDNA3 второго источника. Коэффициент 0.12 пока не подтверждён.
- Флеш-внимание для MoE на Vulkan не разбирали.
- Проверка сборки: сравнивались разные коммиты llama.cpp (от января 2025 до октября 2025), влияние версии не отделено.
