## Что сделано

1. **`docs/COMPATIBILITY.md`**: таблица «карта, драйвер, ОС, бэкенд, модель, скорость, статус, кто проверил, дата». Описаны
   статусы ✓ / ⚠ / ✗ и правило скорости («замер» или «оценка»). Первая строка — наша машина: RX 7800 XT, ROCm 7.1.1 (HIP,
   наш форк), Fedora 44, Tiel-Coder 35B-A3B APEX-I-MiniPlus V2.1; скорость 74 tok/s декода (профиль A, окно 26k, REPORT-PREFILL3),
   44 при 60k и 38 при 150k (профиль B, REPORT-LAYOUT1c). Статус ⚠: работает в нашей ручной раскладке, путь установщика
   на этой машине не проверялся.
2. **`scripts/compat_table.py`**: строит строку таблицы из файла `shura report` (`shura-hardware-report.md`, блок `json`).
   Команды: `show REPORT` (показать строку), `add REPORT --who NAME` (записать строку). Строка одного и того же железа
   (карта, ОС, бэкенд, модель) заменяется, а не дублируется. Скрипт использует только стандартную библиотеку.
   Проверено на настоящем отчёте, который строит `installer/universal/report.py` из фикстуры.
3. **Правило статуса** (`status`): ✗ — план не подходит или установка не проверила сервер; ✓ — сервер работал, а замер
   отличается от оценки не больше чем на 25 %; ⚠ — иначе, в том числе отчёт без замера. Порог 25 % — моё решение,
   взято по разбросу замеров PUB5 (одна карта даёт ±13 % между сборками).
4. **Тесты**: `scripts/test_compat_table.py`, 12 тестов: статусы (пять случаев), построение строки, сообщение для файла
   не того вида, добавление, замена той же машины, другой бэкенд на той же карте, таблица без маркеров. Все проходят.
5. **`.github/ISSUE_TEMPLATE/pilot-report.md`**: шаблон «[pilot] <GPU> on <OS>» с меткой `pilot`. Просит прикрепить
   `shura-hardware-report.md` и не публиковать имена и пути (отчёт их уже не содержит).
6. **README** (`README.md`, `README.ru.md`): в раздел «Подойдёт ли мне?» добавлена ссылка на таблицу совместимости.

## Поправки по передаче от PUB2 и PUB7

- Передача говорила «нужно 19.0 ГиБ RAM» для CPU-режима. Текущий код планировщика даёт **20.2 ГиБ** (проверено на фикстуре
  и на машине с 8 ГБ ОЗУ). README уже писал «около 20 ГиБ», это верно для текущего кода. Цифру 19.0 не использовал.
- Передача говорила, что **6 ГБ видеокарта и 8 ГБ ОЗУ получают явный отказ**. Проверено: да, отказ («needs 20.2 GiB of RAM,
  only 2.0 GiB is available»). Но **6 ГБ видеокарта с 32 ГБ ОЗУ подходит** (гибрид IQ4_XS). Поэтому в README написано про
  сочетание 6 ГБ + 8 ГБ, а не про одну видеокарту. Это добавлено в оба README (PUB7 расширен).

## Решения, которые принял сам

- **Тесты лежат в `scripts/`, а не в `tests/`.** Карточка разрешает менять только `docs/**`, `scripts/**`, `.github/**`.
  Набор `python3 -m unittest discover -s tests` тесты `scripts/` не запускает. Я прогнал их отдельной командой
  (`python3 -m unittest discover -s scripts -p 'test_compat_table.py'`). Если нужно, чтобы они шли вместе с остальными,
  путь `tests/` надо разрешить на доске.
- **`shura doctor` скрипт не разбирает.** Он печатает обычный текст, а не блок `json`. Скрипт понимает только отчёт
  `shura report`. Шаблон просит пилотов прикладывать именно этот файл.
- **Статус ⚠ у нашей машины**, а не ✓: её скорость получена вручную в нашей раскладке, без установщика.

## Что НЕ проверено

- Метка `pilot` на GitHub не создана: это действие в публичном репозитории, а не в файлах. Нужно создать её вручную
  (или дать мне разрешение через `gh`). Шаблон ссылается на метку, но без неё GitHub её не назначит.
- Таблица содержит только одну строку, нашу. Ни одного пилота ещё не было, поэтому правило статуса проверено на фикстурах,
  а не на чужих отчётах.
- `scripts/compat_table.py` не вызывался на настоящем файле `shura report`, снятом с живой машины. Проверено на отчёте,
  который строит тот же код из фикстуры.
- Программа пилотов нигде не анонсирована: ни в README, ни вне репозитория. Публикации не было, по правилам доски.
- Статус ✓ зависит от допуска 25 %, а он выбран по разбросу PUB5; на реальных пилотах может понадобиться другой.
