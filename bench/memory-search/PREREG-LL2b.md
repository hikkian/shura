# LL2b pre-registered rules (written 2026-11-08, before any new query was written or run)

Follows LL2 (`PREREG.md`, `lifelong/reports/REPORT-LL2.md`). Disclosure: the rules below are set knowing the LL2 figures for `stem`
(+5.4 pp hit@3, 95% CI [+2.7; +8.6], extra tokens +29%, no guard group lost). That is why the test is on NEW queries and the rules are fixed now.

## Part 1: does `stem` win on queries it has never seen?
Data: `fixtures/records.json` exactly as in LL2 (not touched). New queries `fixtures/queries2.raw.json` are written blind by a fresh subagent
that sees only the records (not the LL2 queries, not any result, not the search code); typo queries are generated by code from the new
plain queries with a NEW seed (20261109). Arms: `u61` and `stem` decide; `tri` and `both` are re-run for information only.
`stem` WINS only if ALL hold on the new set:
1. hit@3 over all positives is higher than `u61`'s by >= 4.0 pp and the lower bound of the paired 95% bootstrap CI (10,000 resamples) is > 0;
2. in each group `plain_ru`, `plain_en`, `code`, `mixed`, `version`, `stem` is not lower than `u61` by more than 2 pp, unless the loss is a single query;
3. extra tokens per positive query at the operating threshold <= 1.20 x `u61`'s + 1 token (LL2 used 1.10; a gain in recall brings more candidates,
   so 20% is allowed, no more), and the 2-fold false-injection rate <= 10%;
4. p95 latency at 1000 records <= 20 ms, and no deleted record or old version is ever returned.
If `stem` wins: add the flag `memoryStem` (default off; Store parameter + gateway config key) with tests; with the flag off the behaviour stays
byte-identical. If not: no flag, the report says so. The decision is the same whatever LL2's figures were.

## Part 2: memory index inside 1500 tokens
Budget: 1500 tokens = 4500 characters (3 characters per token, as in LL2), header included. Production today: `render_index()` ~2300 tokens at 50 records,
~2950 at 100, and a keys-only list above 100.
Variants (all produced by new code beside the old; the old path stays the default):
`I0` current; `I1` every record as `- key: title`; `I2` tiers (preferences, procedures and confirmed facts with titles; notes, quotes and
unconfirmed records as comma-separated keys); `I3` greedy fill by priority up to the budget, titles cut to 60 characters, the remaining keys
listed compactly as far as they fit, then a line "N more: use memory_search".
Priority: confirmed before proposed, then kind (preference, procedure, fact, note, quote), then more confirmations, then newer.
Measured at N = 129 (the fixture), 200 and 400 (synthetic padding older than the fixture, same priority class): tokens, and for the NEW positive
queries the share whose expected record has its TITLE visible in the index (`title_visible`) and the share with at least its key visible.
Choice: among the variants with tokens <= 1500 at ALL of N = 129, 200, 400, take the highest `title_visible` at N = 129; ties go to the simpler variant
(I1 < I2 < I3). If one is chosen it is added as `Store.render_index(budget_tokens=...)` and the constructor parameter `index_budget_tokens`
(default None = today's output, byte-identical); turning it on is LL6's job. The report also states what the index cannot do (find a note by meaning):
that stays with search.
