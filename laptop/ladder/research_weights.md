## 3. Подробности по пунктам задания

### 3.1. Смешанная точность в llama.cpp

- `llama-quantize` поддерживает [V: S4]: `--output-tensor-type`, `--token-embedding-type`, `--tensor-type <имя>=<тип>` (повторяемый, имя может быть регулярным выражением; пример из README: `--tensor-type "\.(\d*[13579])\.attn_k=q5_k"`), `--imatrix`, `--include-weights` / `--exclude-weights` (применить imatrix только к перечисленным тензорам), `--prune-layers`, `--keep-split`.
- README **не описывает** поведение для 3D-экспертных тензоров [V: прямо сказано, что там этого нет] — детали надо проверять по исходнику `llama-quant.cpp` (на ноутбуке: прочитать локальную копию, если есть сборка). Из IDEAS 1.1 известно (проверено вами): один тип на весь 3D-тензор `ffn_*_exps` в слое, 256 экспертов делят тип. Значит гранулярность выбора — **слой × {gate, up, down}**, а не отдельный эксперт [V].
- Предполагаемая форма команды для слоёв X (имена тензоров ожидаются `blk.N.ffn_{gate,up,down}_exps.weight`; **проверить по `gguf-dump`**) [I]:
  `--tensor-type "blk\.(3|7|11)\.ffn_down_exps=q4_k"`.
- Стоимость по памяти для вашей модели [V по IDEAS]: на один экспертный 3D-тензор Q2_K 88,1 МБ, Q3_K 115,3 МБ, Q4_K 151,0 МБ. Вывод: один тип «все 40×3 тензора» — Q2_K 10,08 ГиБ; Q3_K ≈ 13,2 ГиБ (+3,1); Q4_K ≈ 17,7 ГиБ [I: арифметика 120 тензоров × размеры].
- Сообщество (ik_llama.cpp, рецепты ubergarm) даёт устойчивую практику: **`ffn_down_exps` на одну ступень выше, чем `ffn_(gate|up)_exps`**, внимание/общий эксперт держат выше [V: пересказ карточек в поиске, прямого руководства от ik_llama.cpp не нашёл]. Пример: Kimi-K2 iq3_k для down и iq2_kl для gate/up; GLM-4.5-Air iq4_nl для down и iq4_kss для gate/up [V: S6].
- APEX (mudler): первый и последний слои выше, средние агрессивнее; общий эксперт держать высоко; routed-эксперты 89,6 % весов [V: S5]. Конкретные биты по тирам на странице не указаны [V: не нашёл].
- Unsloth Dynamic 2.0: тип выбирается для каждого слоя отдельно, зависит от модели; метод выбора там описан общо, по эксперту-тензору детали не нашёл [V: S22]. У unsloth есть опубликованный `imatrix_unsloth.gguf_file` (192 МБ) для Qwen3.6-35B-A3B, который можно использовать как готовый imatrix [V: S3; но он не русский, и применим только к Qwen3.6-векторам, а не к Ornith [I]].
- Ваш собственный разбор GSQ-RCO: уже есть в файле Q3_K на 7 тензорах, Q4_K на 1; эмбеддинги/lm_head Q4_K, внимание Q8_0 [V: S12 + IDEAS].

### 3.2. imatrix с русской калибровкой

- Прямого измерения «русская imatrix vs английская для llama.cpp» **не нашёл** [V: поиск без результата].
- Ближайшие данные: Chimoto et al., EACL 2026: при GPTQ/AWQ на Llama3.1-8B и Qwen2.5-7B нецелевая (английская) калибровка хуже; многоязычная улучшает перплексию, а настроенная под язык оценки даёт лучшее; выигрыши скромные (14,88→14,64) [V: S7]. Bielik 7B: польско-английская imatrix заметно лучше без imatrix (Q3_K_M Δp −0,916 → −0,386), но эксперимента «язык калибровки против языка» нет [V: S8].
- Объём: в документации llama-imatrix рекомендации по объёму нет [V: S9]. Практика: ~100–500 тыс. токенов; GSQ-RCO использовало 1 млн токенов, но **до 128 строк на эксперт и порог 32 строки** (если меньше, эксперт не оптимизируется) [V: IDEAS 1.2 по `quantization.json`]. Для нас: русского нужно столько, чтобы «русские» эксперты получили ≥32 строк; считать по счётчику активаций экспертов [I].
- Для MoE: общая проблема нехватки данных на редких экспертах известна; в ik_llama.cpp PR #202 экспертам без данных ставят вес 1 и предупреждают, пока их < 5 % [V: S10]; для mainline сказано, что строгая логика пропуска тензора унаследована от upstream [V: S10 по словам автора]. В LLM Compressor лечат маршрутизацией всех токенов через все эксперты [V: S10].
- Рекомендация [I]: смесь ~35–40 % русского (проза, технический, диалоги, шаблонные слова вроде «Убедитесь», «монторинге»-класса), ~30 % английского, ~30 % код/агентные трассы; сначала `llama-imatrix` на Q8_0 (дёшево по RAM, точнее на BF16), потом смотреть, не пустые ли русские эксперты.
- Объединять imatrix можно (`--in-file a --in-file b -o out`) [V: S9] — удобно: взять готовый английский + доложить русский.

### 3.3. Перефит/поправка квантованных весов без полного обучения

- GSQ (arXiv 2604.18556): скалярный post-training квантизатор с Gumbel-Softmax, закрывает большую часть разрыва до QTIP при 2–3 битах; применялся к K-quant GGUF и к Kimi-K2.5 (MoE); сложность по GPU-часам в карточке/аннотации **не указана** [V: S11]. Код: `IST-DASLab/GSQ`, `IST-DASLab/RCO` [V: S12]. Ваша модель получена именно так (40 шагов Lion, scales/биасы фиксированы) [V: IDEAS].
- Следствие [I]: «GSQ-RU» = запуск того же кода с русской калибровкой, тем же рецептом, но с BF16-источником, что требует GPU, способного прогнать слои 35B с активациями. На RX 7800 XT (16 ГБ, ROCm) совместимость кода DASLab (скорее CUDA/PyTorch) **не проверена**. Времени «за часы» нигде не подтверждено.
- LoftQ (ICLR 2024): чередует квантование и низкоранговое приближение остатка; выигрыш особенно в 2-бит и 2/4 смешанном [V: S13]. ApiQ: сохраняет активации, а не веса; CLoQ: калибровочная инициализация без backprop; QERA: ошибка выхода лучше ошибки весов [V: S13]. Все это инициализации LoRA для **дообучения**; к готовому GGUF с экспертами 3D-формата и llama.cpp LoRA-экспертов поддержка не подтверждена [V: не нашёл].
- Железо: Unsloth даёт 74 ГБ VRAM на bf16 LoRA для Qwen3.5-35B-A3B и не рекомендует MoE-QLoRA 4-bit (пока) [V: S14]; сторонний `transformers-qwen3-moe-fused` заявляет LoRA/QLoRA на 16 ГБ — **заявка проекта, не проверена** [V: S14].
- Вывод [I]: реалистично только для аренды 1×80 ГБ GPU на день; на локальном ПК за часы не нашёл подтверждений.

### 3.4. Словарное ограничение декодирования

- `--grammar`/GBNF: можно задавать токены по ID `<[1000]>` (привязано к токенайзеру) [V: S20]. В официальной документации есть предупреждение: повторы `x?` N раз дают очень медленную выборку; использовать `x{0,N}` [V: S20]. Бенчмарка с огромным словарём **не нашёл**.
- `--logit-bias`: статически запретить/поощрить токены (`ID+bias`/`ID-bias`) [V: S20]. Запрещать «кусочки» (` мон`, `торин`) глобально нельзя: они нужны для обычных слов [I].
- LLGuidance в llama.cpp: поддержка есть в документации (`docs/llguidance.md`); производительность не прочитал [V: S20].
- Практичный подход [I]: свой сэмплер/прокси-слой (в шлюзе): после каждого слова сверять с trie русских словоформ (Hunspell ru_RU, OpenCorpora); если префикс выходит за словарь, ограничивать топ-K токенов теми, которые продолжают допустимый префикс, и только на кириллице; всё, что содержит латиницу/цифры/`_`/`{`/кодовые контексты (внутри ```), не трогать. Риск: имена, жаргон, неологизмы («бэкапы», «кластеризация», «стартапы»), транслитерация.
- Готовой реализации «trie-constrained decoding для русского под llama.cpp» **не нашёл** [V: не найдено].

### 3.5. Слияние Ornith с Qwen3.6

- Репозитории [V: S15, S16 через API HF]:
  - `ornith-ai/Ornith-1.5-35B-A3B`: 16 шардов safetensors, всего **71 926 982 194 Б ≈ 71,9 ГБ (67,0 ГиБ)**, MIT.
  - `Qwen/Qwen3.6-35B-A3B`: 26 шардов, **71 926 859 142 Б ≈ 71,9 ГБ**.
  - Размеры отличаются лишь на 123 КБ (токенайзеры/конфиги), то есть наборы тензоров почти идентичны [I].
- Конфиги: Ornith и Qwen3.6 совпадают по `num_hidden_layers=40`, `num_experts=256`, `num_experts_per_tok=8`, `moe_intermediate_size=512`, `hidden_size=2048`, `vocab_size=248320`, `full_attention_interval=4`, rope-параметрам [V]. Слияние структурно возможно.
- **Внимание:** карточка Ornith пишет, что Ornith-1.0 «developed on top of Qwen3.5 and Gemma4», и не называет Qwen3.6 базой [V: S15]. `base_model` у производных — `ornith-ai/Ornith-1.5-35B-A3B`. Утверждение «дообучение Qwen3.6» — ваша гипотеза [I]. **Проверка до любых планов:** по двум `model.safetensors.index.json` и нескольким шардам оценить, насколько Ornith − Qwen мал относительно Qwen (для настоящего fine-tune отн. разность ~1–5 % на веса, для другого пре-трейна ~100 %) [I]. Читать нужно куски по range-запросам, как вы уже делали в `expert_err.py`.
- Методы: task arithmetic (база + взвешенная сумма дельт), TIES (обрезка по величине + согласование знаков), DARE (случайное обнуление дельт + пересчёт); для гомогенных MoE-слияний DARE/TIES лучше простого усреднения при малых ресурсах (MergeME) [V: S17 через поиск; первичные статьи сам не открывал]. WiSE-FT-подтверждений не нашёл [V].
- Особенности MoE [I]: интерполировать надо одинаково `router.weight`, `experts.*`, `shared_expert.*`; слияние роутера смещает выбор экспертов и может ломать совместное приспособление роутер/эксперт; начинать с α, одинакового на все тензоры; потом пробовать α только на экспертах/внимании.
- Реальный пайплайн [I]: потоковое слияние по шардам (python+safetensors, без `pip install` — на ПК, уже имеющий окружение) → HF-каталог BF16 ~72 ГБ → `convert_hf_to_gguf.py` → BF16 GGUF → `llama-imatrix` → `llama-quantize` → замер. Диск ≈ 72 (A) + 72 (B) + 72 (результат) + 72 (GGUF BF16) + 15–25 (кванты) — практически **250–300 ГБ**, если хранить всё; можно удалять по ходу.
- Ожидание: α=0,3–0,5 вернёт часть русской стойкости Qwen, но это пара «стойкость против агентности» — измерять оба (опечатки + ваш набор 19 заданий) [I].

### 3.6. Способ измерения

- **llama-perplexity**: двухшаговая схема KL [V: S23]: (1) `llama-perplexity -m <эталон> -f ru.txt --kl-divergence-base base.kld` (сохраняет логиты эталона); (2) `llama-perplexity -m <кандидат> -f ru.txt --kl-divergence-base base.kld --kl-divergence` (выдаёт KL, ratio PPL, top-token agreement). Нужен один и тот же текст и словарь.
- Размер `.kld`: для LLaMA 3 (словарь 128k) на wikitext-2 ~37 ГиБ [V: S23]; у вашей модели словарь 248k, значит ≈ ×1,9 на токен [I]: 50 тыс. токенов ≈ 10–15 ГБ [I: оценка по пропорции]. Планируйте диск.
- Эталон: Q8_0 Ornith (37,8 ГБ, официальный) — достаточно близок к BF16, помещается на ПК с выгрузкой экспертов на CPU [I]; если BF16 (71 ГБ) не влезает в 32 ГБ RAM, mmap с диска медленный (час-два на 50 тыс. токенов) [I].
- **Счётчик опечаток** (ваш `ruspell`): минимально надёжный объём, чтобы различать 0,6 и 1,2 на 1000 слов: Пуассон, точный биномиальный тест на отношение 1:2 при α=0,05 двусторонний: мощность 79 % при 70 событиях, 82 % при 80, 90 % при 100 [V: посчитал сам, python stdlib]. Ожидаемых событий в сумме обоих вариантов 1,8 на 1000 слов, значит **~40 тыс. слов на вариант (≈80 тыс. всего) для мощности ~80 %**; для 90 % ~55 тыс. [I]. На меньших выборках (10 тыс. слов) 0,6 против 1,2 различимы лишь с мощностью ~30 % [I]; значит маленькими пробами нельзя утверждать улучшение вдвое.
- Дешёвые прокси до счётчика [I]: «запас правильной буквы» на фиксированном списке трудных слов (из IDEAS, фаза 0), KL на русском тексте, среднее логарифма вероятности «правильного» слова на словарном списке.

## 4. Пошаговый план первого эксперимента (общие команды, не запускать на ноутбуке)

Цель: ответить «проблема в кванте или в модели» и сколько нужно битов.

0. Подготовка (ПК). Свободно ≥ 120 ГБ диска. Остановить прочие llama-server на ПК. Проверка списка: `ls`, `df -h`.
1. Скачать официальные Q4_K_M (21,7 ГБ) и Q8_0 (37,8 ГБ) `ornith-ai/Ornith-1.5-35B-A3B-GGUF` (`hf download` или `curl -L` по `resolve/main/<файл>`; проверить sha256 с HF-страницы).
2. Корпус: `ruspell` в объёме **≥ 40 тыс. слов на вариант** (повторы с разным seed допустимы, но тексты должны быть разные); те же промпты для всех вариантов.
3. Запуск (шаблон):
   `llama-server -m <gguf> -ngl 99 --n-cpu-moe 40 -c 8192 --port <тестовый>` (на ПК порт не 8080/8090), температура как в `ruspell` (T=0,4).
4. Счётчик опечаток: ваш `ruspell/*.py` на каждом варианте, фиксировать число опечаток и слов. Принять решение по `DECISION-RULE.txt`.
5. KL-замер на русском тексте 30–50 тыс. токенов:
   `llama-perplexity -m Q8_0.gguf -f ru_eval.txt -c 512 --kl-divergence-base q8.kld -ngl 99 --n-cpu-moe 40`
   `llama-perplexity -m <кандидат>.gguf -f ru_eval.txt -c 512 --kl-divergence-base q8.kld --kl-divergence -ngl 99 --n-cpu-moe 40`
   Сравнить KL, «same top p», ΔPPL между: GSQ-RCO 3-bit, Q4_K_M, Q5_K_M, (по желанию) APEX Compact.
6. Если Q4_K_M ≥ 2× лучше по опечаткам (например 0,6 вместо 3): выбор готовый, переходить к скорости и MTP.
7. Если нужно уменьшить размер (13–16 ГБ) с лучшим русским: из BF16 (71 ГБ) собрать микс.
   - imatrix: `llama-imatrix -m Ornith-1.5-35B-BF16.gguf -f mix_ru30_en30_code30.txt --chunks N -ngl 99 --n-cpu-moe 40 -o imat_ru.gguf` (или на Q8_0; BF16 на 32 ГБ RAM будет медленным). Смотреть вывод о пропущенных тензорах/экспертах.
   - квантование: `llama-quantize --imatrix imat_ru.gguf --tensor-type "blk\.\d+\.ffn_down_exps=q4_k" --tensor-type "blk\.\d+\.ffn_(gate|up)_exps=q3_k" --token-embedding-type q6_k --output-tensor-type q6_k Ornith-1.5-35B-BF16.gguf out.gguf Q3_K_M` (общий вид; **проверить имена тензоров по `gguf-dump` и поведение регулярок на 3D-тензорах**). Размер ориентировочно: down Q4_K + gate/up Q3_K ≈ 15,5 ГиБ экспертов [I].
   - затем повторить шаги 4–5.
8. Ограниченное повышение (вариант C, самый дешёвый по ресурсам): из имеющегося файла заменить `ffn_down_exps` в слоях, которые чаще участвуют в русском (по трассе активаций), на Q4_K; это тот же приём, что `lmhead/build.py`; брать **Q4_K из BF16**, не из Q2_K (требантование из Q2_K бессмысленно: информация потеряна) [I].

Решение: по `DECISION-RULE.txt` + порог: ≤1,0/1000 на ≥40 тыс. слов = «хорошо».
